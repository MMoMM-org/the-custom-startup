## Reporting

Your final message is read by an automated orchestrator that routes on its first line, so begin the message with exactly one of these status words on a line by itself:

- `DONE`: the task is fully implemented, tests pass, and the work is committed. You have no concerns that bear on correctness or scope.
- `DONE_WITH_CONCERNS`: the task is implemented, tests pass, and the work is committed, but you have doubts. State each concern and label it either `correctness/scope` (you may have built the wrong thing, the design looks flawed, requirements conflict, behavior is untested or uncertain, you had to go outside the task's scope) or `observation` (style, follow-up ideas, unrelated issues you noticed, minor notes). Only use this when you actually have concerns; do not hedge a clean result.
- `NEEDS_CONTEXT`: you cannot proceed correctly because specific information is missing (an undefined interface, an ambiguous requirement, a file or decision the task assumes but that does not exist). List precisely what you need, as numbered questions. Do not commit partial guesses. Leave the working tree as you found it, or describe any changes you left.
- `BLOCKED`: you tried and cannot complete the task. State which kind of block it is, so it can be routed:
  - `context`: information you lack (prefer NEEDS_CONTEXT if it is a clear question)
  - `too-complex`: the task is beyond what you can implement reliably, and say what you tried and where it failed
  - `too-large`: the task is really several tasks. Propose a split
  - `plan-wrong`: the task's premise is contradicted by the repository or the design, and say what is contradicted and the evidence
