<!-- 2026-05-09 -->
- **Bash 3.2 regex (macOS default `/bin/bash`):** `\s` and `\b` are PCRE/Perl extensions and do **NOT** match in `[[ =~ ]]` (POSIX ERE). Empirically verified on bash 3.2.57. Use `[[:space:]]+` for whitespace and `[[:<:]]` / `[[:>:]]` for word boundaries (BSD POSIX). Quick test: `[[ "git push" =~ git\\s+push ]] && echo M || echo NM` prints `NM`; `[[ "git push" =~ git[[:space:]]+push ]]` prints `M`. Forget this and command-matching hooks silently never fire.
- **`gh pr view --json mergeMethod` does NOT exist** (verified gh CLI 2.88.1) — returns `Unknown JSON field: "mergeMethod"`. To detect squash-vs-merge after the fact: `gh pr view <num> --json mergeCommit --jq '.mergeCommit.oid'` to get the merge SHA, then `git rev-list --parents -n 1 <sha> | awk '{print NF-1}'` — parent count `1` = squash/rebase, `2` = merge-commit. Primary squash detector should be `git cherry origin/<default> <branch>` (all `-` lines = patches already applied).
- **Claude Code hook event blockability:** `PreToolUse:ExitWorktree` is a blockable native tool — supports `permissionDecision: deny` JSON. `WorktreeRemove` and `SessionEnd` are documented as non-blockable ("failures logged in debug mode only"). For worktree-exit data-loss guards, register on `PreToolUse:ExitWorktree`. Boucle-framework's `worktree-guard` confirms this pattern.
- **Boucle-framework as prior art for git-safety hooks** — `github.com/Bande-a-Bonnot/Boucle-framework/tree/main/tools` has three relevant Claude-Code hook tools: `git-safe` (destructive-ops prevention with regex pattern set covering `--no-verify`, `reset --hard`, `clean -f`, `branch -D`, `stash drop/clear`, `reflog expire`, etc.), `branch-guard` (protected-branch commit blocking with `.branch-guard` config), `worktree-guard` (exit-time data-loss prevention with 4 checks via `git cherry`). Re-implement (not vendor) — patterns absorbed into `tcs-git-helpers` plugin.

- **bats `! cmd` mid-test silently passes** (bats 1.5+) — bare `! cmd` only fails the test when it is the LAST command in the `@test` body. Non-final `!` assertions silently pass even when the negation actually fails. Symptom: `! _match_command "git push"; do_other_stuff` reports `ok` even if `_match_command` matched. Workaround: define a `_no_match` helper that returns 1 on unwanted match, so `set -e` triggers test failure. Discovered empirically by injecting deliberate failure mid-test (spec-011 T1.5 dispatch).
- **bash 3.2 bounded-quantifier `^.{m,n}$` regex broken** in `[[ =~ ]]` — `[[ "53-char-string" =~ ^.{0,256}$ ]]` returns false despite the input clearly matching. Workaround: drop the bounded quantifier and use explicit length check `[ "${#var}" -gt N ]`. Complements the existing `\s`/`\b` PCRE-extension note above; together they describe the major bash 3.2 regex traps.
- **bash glob `*$'\0'*` matches everything** — `$'\0'` (ANSI-C NUL) expands to empty string in bash, so `case "$x" in *$'\0'*) … esac` becomes effectively `case "$x" in **) … esac`. Bash strings cannot contain NUL bytes anyway. Don't use `$'\0'` in case-globs for "reject NUL" — use `read -r` plus per-key allowlist instead.
- **jq + `set -euo pipefail` = fail-closed Claude Code hooks** — `VAR=$(printf '%s' "$INPUT" | jq -r '.field // ""')` propagates jq's exit code under `set -e`, so malformed JSON (or missing jq) makes the hook exit non-zero, which Claude Code interprets as "deny tool call". Hooks meant to fail-OPEN MUST append `2>/dev/null || true` to every jq command-substitution. T2.3, T2.2, T2.1 all shipped this trap initially; only T2.4 (which used `set -uo pipefail` with no `-e`) was immune. Mirror the `lib/audit_log.sh` pattern when writing new hooks.
- **macOS sandbox `mktemp -d` quirk** — even though `/var/folders/` is in the sandbox writable allowlist, `mktemp -d` (default `$TMPDIR`) consistently fails with "Operation not permitted" when invoked from harness Bash. Workaround for bats setup: `TMP_DIR="$(mktemp -d "${TMPDIR:-/tmp}/myname-XXXXXX")"`. Or run with `dangerouslyDisableSandbox: true`. NEVER use `${TMPDIR:-/tmp}/$RANDOM` (no XXXXXX template) — same failure mode.
- **build.sh-in-parent-repo pollution mode** — bats fixtures that run `git init` inside a tempdir can silently leak commits onto the parent branch when `mktemp -d` fails (see entry above). The failed-init falls back to the parent `.git/` and subsequent `git add/commit` lands on the parent branch. Symptom: 30 stray "init/feat-1/feat-2" author=`t` commits on the feature branch (spec-011 T2.1 incident). Hardening for fixture builders: `mktemp -d "${TMPDIR:-/tmp}/...XXXXXX"` AND `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null` in the test subshell AND `git -C "$tmpdir"` (never bare `git`). Reference `plugins/tcs-git-helpers/tests/fixtures/repos/build.sh` as the canonical pattern.

- **bats test-registration locking pattern** — for integration tests that verify hook registrations in `hooks.json` (e.g., T3.4), write a dedicated bats file (e.g., `hooks-json.bats`) with jq assertions covering: valid JSON, all required hook entry points present, scripts registered under correct matchers, paths use `${CLAUDE_PLUGIN_ROOT}` convention, no unknown top-level keys (future-drift detection). Setup resolves `PLUGIN_ROOT="${BATS_TEST_DIRNAME}/../.."` and `HOOKS_JSON="${PLUGIN_ROOT}/hooks/hooks.json"`. Example: `jq -e '.hooks.PreToolUse[] | select(.matcher == "Bash") | .hooks[] | select(.command | contains("block-bad-git-ops.sh"))'` for a single matcher+script combo. This pattern ensures registration changes (e.g., adding a new hook) don't silently drift out of sync with documentation.
- **bats non-final assertion scope clarification** — the `! cmd` mid-test trap above (L13) applies ONLY to negation. Standard mid-test assertions (`[ "$x" -eq 0 ]`, `grep -q pattern`, bare `false`) DO fail the test correctly when the condition is unmet — verified empirically with `bats 1.12` on macOS by running a test body of `X=1; [ "$X" -eq 99 ]; true` (got `not ok` on the bracket line). Reviewers in spec-011 T3.2/T3.3 reviews over-extended the rule and flagged correct test layouts as broken; orchestrator rejected with this empirical proof. Don't generalize the negation-only trap to all assertions.
- **Perf tests with caching/dedup must reset state per iteration** — looped invocations of a hook that has dedup (e.g., 60s nudge dedup via sentinel file) measure the cheap suppression path on iterations 2..N, not the production trigger path. Initial T3.3 bats perf test reported "33ms p99" but was actually measuring `date`+`cat` on the early-exit branch; honest measurement after `rm -f $CACHE/*-nudge-* 2>/dev/null` per iteration was 34ms p99 (within budget but not by accident). Pattern: clear all dedup/cache artifacts at the top of every iteration, OR vary the keying input per iteration so dedup keys never collide. Without this, a regression to 200ms in the trigger path would silently pass.

- **`CLAUDE_PLUGIN_ROOT` / `CLAUDE_PLUGIN_DATA` are harness-spawned only** — the Claude Code harness sets these env vars when *it* directly spawns plugin code (settings.json `${CLAUDE_PLUGIN_ROOT}/scripts/...` hooks, plugin `hooks.json` registrations, skill-invoked Bash). They are NOT propagated to git-spawned subprocesses (git hooks like `.githooks/post-merge` fired by `git merge`) NOR to processes spawned by the Bash tool. `CLAUDE_CODE_SESSION_ID` and `CLAUDECODE=1` DO propagate through git. Verified empirically 2026-05-13 via 3-context env probe in this repo. Implication: plugin code that runs in git-hook context (any `templates/githooks/*` installed via `core.hooksPath`) cannot rely on these env vars — it must self-derive paths, inline its dependencies, or accept install-time substitution. This is the root architectural cause behind spec/012 (`docs/XDD/specs/012-tcs-git-helpers-hook-runtime-contract/`).

- **gh-stub wire-format extends to `--jq` filtering** — the existing rule that CLI stubs must mirror real wire format (`feedback_test-stubs-mirror-real-wire-format.md`) covers the `--json` envelope shape but is incomplete if the stub naively `cat`s the response file when the caller passes `--jq <expr>`. Real `gh` applies the jq filter server-side, returning just the extracted value. A stub that ignores `--jq` returns the whole envelope, silently diverging from prod. Spec-014 T1.3 had this exact bug: cache-miss test wrote `{"mergeCommit":{"oid":"…"}}` to the cache instead of just the SHA — production with real gh would have written `"…"`. Fix pattern: scan args for `--jq <expr>` or `--jq=<expr>`, when present pipe `_emit_response <op> | jq -r "$expr"`. See `plugins/tcs-git-helpers/tests/fixtures/gh_stubs/gh` (pr view branch).
- **bats `run --separate-stderr` discards variable mutations from the function under test** — `run` always invokes its argument in a `()` subshell, so any `OVERRIDE_VAR=...`, `local`/global var, or shell-state mutation by the called function is lost to the test body. With `--separate-stderr` this is unavoidable. Pattern: split tests by concern — one test asserts side-effect variables (call function directly, no `run`); a sibling test asserts stderr (use `run --separate-stderr`, only assert `$status` + `$stderr`). Verified in `plugins/tcs-git-helpers/tests/bats/lib_override.bats:201-207` (env-var path) and `:455-466` (scan-path master). Don't try to assert both in one test — you'll either skip the stderr or read stale vars and chase phantom bugs.

- **Claude Code's Bash tool reaps the command's process group at the tool-call boundary** — a server spawned with `nohup … & ; disown` survives the launching command but is killed (silently — SIGKILL, no graceful shutdown) the moment that Bash tool call returns. `nohup`/`disown` only block SIGHUP, not the harness teardown. Symptom in the brainstorm visual companion: served exactly one screen, then gone before the next push, with no `server-stopped` marker and no JS stack trace (= external signal, not the skill's own lifecycle). Fix: run the process in **foreground** (`start-server.sh --foreground`) inside a Bash tool call with `run_in_background: true`, then read connection info from a state file on the next turn — a background tool call persists across turns. Verified empirically: a server started in one tool call was DEAD in a later same-turn call; the foreground+background variant answered HTTP 200 across the boundary. `ps` is also sandbox-blocked (`operation not permitted`), so any owner-PID process-walk in a launch script silently degrades. `CLAUDECODE=1` is set in the harness env (and propagates through git) so scripts can detect it. Relates to the `CLAUDE_PLUGIN_ROOT` harness-spawn entry (2026-05-13) and the agents-never-get-a-TTY rule.
