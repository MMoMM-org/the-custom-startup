# Skeleton: Python Tool

This file describes the proposed `docs/` tree for a Python tool or CLI repository.
`plan` mode reads this skeleton and creates the pages listed below as empty
placeholder files. Each page entry states its purpose and the section structure
a first-time author should follow when writing the content.

---

## Proposed docs/ tree

```
docs/
├── README.md
├── installation.md
├── configuration.md
├── usage.md
├── troubleshooting.md
└── quickstart.md
```

---

## Page Descriptions

### docs/README.md

**Purpose:** Top-level index that orients any reader landing in the `docs/` directory.
Links to every other page so the tree is navigable from the root.

**Suggested section structure:**

- H2 `## Overview` — one paragraph describing what the tool does, the problem it solves,
  and who it is for.
- H2 `## Documentation map` — bulleted list of links to every page in `docs/`:
  `installation.md`, `configuration.md`, `usage.md`, `troubleshooting.md`,
  `quickstart.md`.
- H2 `## Quick links` — optional; direct links to the fastest paths (e.g.
  "Install via pip", "First command", "Configuration reference").

---

### docs/installation.md

**Purpose:** Guides a new user from zero to a working installation of the tool,
covering standard and alternative install paths and verification.

**Suggested section structure:**

- H2 `## Prerequisites` — Python version requirement (e.g. `>= 3.10`); any system
  packages required before pip install.
- H2 `## Install via pip` — `pip install <package-name>` (or `uv add <package-name>`
  for uv-managed projects); recommended virtual environment setup steps.
- H2 `## Install from source` — `git clone`, `cd`, `pip install -e .` (or
  `uv sync`); for contributors or pre-release testers.
- H2 `## Verify the installation` — the exact command that proves the tool is
  installed and responding (e.g. `<tool> --version` or `<tool> --help`);
  expected output snippet.
- H2 `## Upgrading` — `pip install --upgrade <package-name>`; note any breaking
  changes procedure if applicable.

---

### docs/configuration.md

**Purpose:** Documents every user-configurable option exposed by the tool: name,
type, default value, and what it controls. Generated by `extract` mode from the
Pydantic model, dataclass, or JSON Schema that defines configuration. Authors
should not edit this page by hand — re-run `extract` when settings change.

**Suggested section structure:**

- H2 `## Configuration sources` — precedence order (e.g. CLI flags override env
  vars override config file override defaults).
- H2 `## Config file` — path and format (TOML, YAML, JSON); how to create one;
  example minimal config.
- H2 `## Settings reference` — Markdown table: `Name | Type | Default | Description`
  (one row per setting, produced by `extract` mode).
- H2 `## Environment variables` — any settings that can also be set via env var;
  naming convention (`TOOL_SETTING_NAME`).

---

### docs/quickstart.md

**Purpose:** Shows a new user the first command to run after installation so they
experience the tool's value immediately. Covers the most common single use case
end-to-end without requiring any configuration.

**Suggested section structure:**

- H2 `## Your first command` — the one command that demonstrates the tool's primary
  function; exact invocation with sample input and expected output.
- H2 `## What just happened` — brief explanation of what the tool did in that run,
  helping the user build a mental model before exploring further.
- H2 `## Next steps` — links to `usage.md` for more workflows and `configuration.md`
  to customise behaviour.

---

### docs/usage.md

**Purpose:** Describes the full range of ways a user interacts with the tool once
they are past the quickstart. Covers the command surface and common workflows.

**Suggested section structure:**

- H2 `## Command reference` — brief table or list of every sub-command or flag with
  a one-sentence description; links to deeper pages if the tool is large.
- H2 `## Common workflows` — 2–5 named, end-to-end patterns a real user will repeat
  (e.g. "Process a batch of files", "Run in CI", "Integrate with another tool").
- H2 `## Tips` — non-obvious invocations, shell aliases worth setting, stdin/stdout
  composition patterns.
- H2 `## Examples` — optional; concrete invocations with real-looking inputs and
  annotated outputs.

---

### docs/troubleshooting.md

**Purpose:** Helps a user recover from the most common failure modes without reaching
the tool author. Written from the user's symptom, not the author's debugging model.

**Suggested section structure:**

- H2 `## Common issues` — one H3 per issue: symptom as heading, cause, fix steps.
  At minimum: "Command not found after install", "Import error on first run",
  "Unexpected output or silent failure".
- H2 `## Debug mode` — how to enable verbose/debug output (e.g. `--verbose`,
  `LOG_LEVEL=DEBUG`); what to look for in the output.
- H2 `## Filing a bug report` — what to include (Python version, OS, pip freeze
  output, exact command, full error traceback); where to file (GitHub Issues URL).
